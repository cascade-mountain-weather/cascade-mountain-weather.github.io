# Cascade Mountain Weather

Jekyll site on GitHub Pages (custom domain via `CNAME`) with weekly weekend ski forecasts for Washington Cascades areas, live weather/model tools, and a forecast-evaluation page. Built by GitHub Pages' own Jekyll pipeline on push — no GitHub Actions build/deploy step for the site itself. See `PLAN.md` for the in-progress UI/feature revamp for this season.

Areas covered: Mt. Baker, Stevens Pass, Snoqualmie Pass, Blewett Pass, Crystal, Paradise, White Pass, Hurricane Ridge, Washington Pass.

**Migrated from hand-duplicated HTML to Jekyll in September 2026** (see git history around that date) to remove the header/nav/footer duplication across ~35 pages and replace fetch-and-probe JavaScript (scanning for post files by guessing filenames) with native Jekyll collections/Liquid. Old posts were kept as HTML content (not converted to Markdown) with front matter added; only the shared chrome moved into layouts/includes.

## Layout

- `_config.yml`: site config, defaults, `exclude:` list (Python-only folders like `scripts/`, `data/`, and non-site docs are excluded from the build — check this list before adding new top-level files, since anything not excluded gets copied into `_site` and deployed).
- `_includes/`: `head.html` (meta/SEO/GA), `header.html`, `nav.html`, `footer.html`, `pwa-scripts.html` (header.js + service worker registration + offline banner, included on every page).
- `_layouts/`: `page.html` (default full-doc layout for standalone pages), `post.html` (wraps forecast posts in the post-header/post-content/post-footer structure), `home.html` (bespoke, for `index.html` only — has the page-loader, satellite looper, and DGZ education content).
- `_posts/YYYY-MM-DD-weekend-forecast.html`: one file per forecast post, front matter + body only (no `<html>/<head>/<header>` boilerplate — that's the layout's job). Front matter fields: `title`, `description`, `keywords`, `tagline`/`summary` (used by the homepage hero for the latest post), `forecast_period` (just the date range text), optional `closing_note`. The date comes from the filename. Jekyll's `permalink` in `_config.yml` keeps the historical URL scheme `/posts/YYYY-MM-DD-weekend-forecast.html`, so old links and `../assets/...` image paths inside post bodies still work unchanged.
- `posts/TEMPLATE-post.html`: copy-paste starting point for a new post (excluded from the build via `_config.yml`, never published itself). `posts/archive.html` and `posts/post-style.css` remain in `posts/`, not `_posts/`, since they aren't dated posts.
- Top-level pages (`about.html`, `model-tools.html`, `evaluation.html`, `sitemap-page.html`, `tools/*.html`, `index.html`) are Jekyll pages: front matter (`layout`, `title`, `description`, etc.) + body content only.
- `assets/images/YYYYMMDD_fx/`: figures for each week's post (folder date matches the post date). `assets/images/satellite/`, `gfs_dgz_F48.png`, `assets/data/radiosonde_history.json`: auto-generated by workflows — do not hand-edit. The history JSON lives under `assets/` (not `data/`, which is excluded from the build) specifically so it's servable to the client for the trend chart on `tools/radiosonde.html`; see `scripts/collect_radiosonde_history.py` and the `radiosonde_history.yml` workflow.
- `assets/data/live_conditions.json` (every 2 h, `scripts/collect_live_conditions.py`) and `assets/data/normals.json` (daily, `scripts/collect_normals.py`) are bot-generated from `_data/areas.yml`; do not hand-edit. `assets/data/basins.geojson` is static (`scripts/build_basins.py`). The normals script reads a cached 1991-2020 temperature climatology (daily mean plus 25th/50th/75th percentiles, used for the popup charts) in `data/snotel/tavg_climo.json`; rebuild it with `--rebuild-climo` when a SNOTEL station is added.
- **Radiosonde skew-Ts are pre-rendered** (Oct 2026): `scripts/radiosonde_skewt.py` (MetPy, deps in `scripts/requirements-skewt.txt`, workflow `radiosonde_skewt.yml`, several runs after each 00Z/12Z) writes PNGs and `manifest.json` to `assets/data/radiosonde/` (newest 8 cycles per station; bot-generated, do not hand-edit). `assets/radiosonde.js` just reads the manifest; there is no in-browser Python anymore. Header logo/photo have small mobile copies (`cmw_logo-256.png`, `cascade_pano-mobile.jpeg`); the originals are kept.
- `tools/model-tools-current-weather.html` is now only a redirect to the live conditions map (the old current-weather table and its hourly bot were removed). `scripts/collect_weather_data.py` is retired and kept only for its station mapping.
- **Evaluation (replaced Oct 2026):** `evaluation.html` is a client-side page driven by `assets/data/evaluation.json` (`assets/evaluation.js`, `assets/evaluation.css`), with a season selector. Per forecast: `scripts/nbm_snapshot.py` saves the NBM at forecast time, `scripts/score_forecast.py` scores it (observations in `scripts/snotel_obs.py`; your ranges are read from the posts by `scripts/ours_from_posts.py`), and `scripts/build_evaluation_json.py` rebuilds the page data. Seasons run September to August; add a new one to `SEASONS` in `build_evaluation_json.py`. The 2025-26 season was rebuilt with `scripts/backfill_evaluation.py`. The original page is archived at `evaluation-2025-26-original.html` (noindex); its scripts (`populate_evaluation_html.py`, `build_fx_evaluation.py`, etc.) are retired. **HRRR and HRDPS** (`scripts/hires_models.py`, read through Herbie) are saved into each snapshot under `hires` for the windows they reach in 48 hours (Friday) and scored on a "Friday only" view of the page; HRRR was backfilled for 2025-26 with `scripts/backfill_hires.py`, HRDPS is not archived so it starts with 2026-27 (its snowfall assumes 10:1). **CoCoRaHS** volunteer reports within 25 km (`scripts/cocorahs_obs.py`) are saved as a cross-check, not a score. The precipitation tools page draws HRRR and HRDPS over the NBM plume from `assets/data/hires_plumes.json` (`scripts/hires_plume.py`, workflow `model_data.yml`, which also builds the NBM plumes and the meteograms).
- **Sub-seasonal weather regimes and S2S alert** (Nov 2026): `scripts/fetch_subseasonal.py` saves the IRI/CW3E regime figures to `assets/data/subseasonal/` (bot-generated) every Wednesday; `scripts/check_s2s_update.py` watches CW3E's S&S Outlooks RSS feed (last post in `data/s2s/last_seen.json`) and the workflow `s2s_update.yml` opens a GitHub issue labeled `s2s-update` for a new post. `assets/model-viewer.js` has an opt-in side-by-side mode (a view returns `compare: [{label, view}, {label, view}]`; pages add a `layout` selector).
- **Powder Stash Predictor** (Nov 2026, `in-house/powder-stash.html`, name in `_config.yml` as `powder_model_name`): five-day ECMWF anomaly viewer plus a storm-pattern call and a zone map of how much more or less water a pattern brings than a normal storm. `scripts/pattern_model.py` builds `data/forecast_model/` (pattern centres, ERA5 baseline, zone table; committed, small) from the ERA5 storm-day analysis (`storm_idisp.py --k 6` must have run); `scripts/pattern_forecast.py` reads ECMWF open data (det and 50-member ENS, 12-hourly to 120 h), classifies each member and writes frames and JSON to `assets/forecast/` (gitignored). The page reads them from the `forecast-data` branch (`forecast_data_url` in `_config.yml`, same force-pushed single-commit approach as the satellite looper; the workflow is not built yet) and falls back to the local `assets/forecast/`. `assets/pattern-forecast.js` draws everything; its zone maps use `assets/data/basins.geojson` and `assets/data/pnw_basemap.json` (`scripts/build_pnw_basemap.py`). Dry/wet labels come from the median member's precipitation over the Cascades box. **Mt. Hood** (Mt Hood Test Site SNOTEL 651, `EXTRA_STATIONS` in `scripts/storm_zones.py`) is an extra zone: scored against the mean of the nine Washington zones, but it does not enter the storm-day mean or any Washington zone's baseline, so adding it changed none of the existing numbers. Its map polygon is HUC8 17070105 in `assets/data/basins.geojson` (rebuilt with `scripts/build_basins.py`).
- **Secrets:** never commit tokens. The Synoptic token is the `SYNOPTIC_TOKEN` repository secret (Settings > Secrets and variables > Actions); `collect_live_conditions.py` reads it from the environment and exits if it is missing. To run them locally, set the variable first. Workflows declare `permissions: contents: write` explicitly. CDN scripts and stylesheets carry `integrity` hashes; if you change a CDN version, recompute the hash (`openssl dgst -sha384 -binary FILE | openssl base64 -A`). Links that open a new tab need `rel="noopener noreferrer"`.
- `data/`, `scripts/`, `cascade_weather_app/`: excluded from the Jekyll build entirely (Python/Flutter inputs, not served).
- PWA: `manifest.json`, `service-worker.js`. Bump the cache version in `service-worker.js` if cached assets change.
- `sitemap.xml` is now generated at build time by the `jekyll-sitemap` plugin — it is **not** a source file and must not be hand-edited or committed; `scripts/generate_sitemap.py` and its workflow were removed.

## How things connect

- The homepage "Latest Forecast" card and `posts/archive.html` ("Previous Forecasts", a year/month selector over every post) are both driven by `site.posts` (Liquid), sorted newest-first automatically by Jekyll. There is no `latest-post-summary.html` anymore and no client-side fetch/probe JS for posts — publishing a new post file is the only step needed to update both.
- `_includes/head.html` appends " | Cascade Mountain Weather" to post `<title>`/og:title automatically (posts' front matter `title` is just the plain heading text, matching what shows in the post header/archive/recent-posts list).

## Local preview

Ruby/Jekyll are installed locally. From the repo root: `jekyll build` (or `bundle exec jekyll build` using the checked-in `Gemfile`) to build into `_site/` (gitignored), or `jekyll serve` to preview at `http://localhost:4000` with live reload. Always do this before pushing a structural/layout change — GitHub Pages' build environment is otherwise the first place a Liquid error would surface.

## Git and workflow

- Remotes: `origin` = cascade-mountain-weather.github.io, `upstream` = Cascski-Alpine-Insights. Default branch is `main`. Danny works on branch `danny` (a `clinton` branch also exists) and merges via PR into `main`.
- Bots push constantly to `main` ("Update weather data [skip ci]", "Update GFS plot", "Update satellite looper assets"). Expect `git pull --rebase` before pushing, and never hand-resolve conflicts in the auto-generated files by editing them, just take the bot's version.
- Commit messages are short and lowercase-ish (e.g. "posting this week's forecast", "update latest post").

## Conventions and gotchas

- Forecast posts are written in an informal, humorous voice with an emoji-laden tagline. When editing post prose, preserve Danny's voice and never invent forecast numbers, model output, or observations. Ask for them.
- The README, QUICK-GUIDE, and EVALUATION-GUIDE predate the Jekyll migration and describe the old structure (raw HTML posts, manual archive/homepage edits, `Dawg-Winter-Weather-Blog` repo name). Trust this file and the code over them until they're rewritten.
- Image files in `assets/images/*_fx/` are large (up to several MB). Don't re-encode or delete them without asking.
- Paths contain spaces (`OneDrive - UW`), so quote them in shell commands. Shell is PowerShell on Windows, with Git Bash also available; Bash invocations in this OneDrive-synced folder can take ~90s to start (first-run/AV scan), not a hang — give commands time before assuming they're stuck.
- `_includes/lightbox.html` (wired into all three layouts) gives click-to-enlarge/swipe-through behavior to `<img>` tags, but it's opt-in via class: add `PlotFormat` (the existing convention for post/tools-page figures), `SynopticPlot` (synoptic tools page), or the generic `lightbox-img` class to any new image that should get it. See `assets/lightbox.js`.

## Skills in this repo

- `/new-forecast-post`: scaffold a weekly post as a new `_posts/` file from the template.
- `/run-evaluation`: score the latest weekend and refresh the evaluation page data.
- `/site-check`: sanity-check front matter, leftover template markers, and image references before pushing; optionally run a Jekyll build to catch Liquid errors.
